# dataset.md — Understanding `configs/finetune.yaml`

This is a teaching document, not a spec. It walks through every value in
`configs/finetune.yaml`, why it's there, and why it's set the way it is —
assuming you're new to audio signal processing. Read top to bottom; later
sections build on earlier ones.

---

## 1. The big picture first

We're building a **denoiser**: a model that takes noisy speech (a soldier's
voice recorded near gunfire, engines, wind) and outputs clean speech. To
train that model, we need *paired examples*: (noisy audio, clean audio)
where both are the same sentence, just one has noise added and one doesn't.

We don't have real recordings of "the same sentence with and without
gunfire" — nobody records that pair in real life. So we fake it, on
purpose, in a controlled way: take real clean speech, take real noise, mix
them together at a known intensity, and now we have a perfect pair — because
we made the noisy one ourselves, we know exactly what the clean target
should be.

Every value in `finetune.yaml` controls some part of *how* we fake that
mixture so it's realistic enough that a model trained on it generalizes to
real battlefield audio.

### 🧠 Intuition
Think of it like training a stunt driver. You can't let them learn by
crashing real cars on public roads. So you build a controlled track with
obstacles you fully control — placed at known distances, known speeds — and
you make the track varied enough (rain, night, gravel) that skills learned
there transfer to the real road. `finetune.yaml` is the blueprint for our
"track": how loud the noise is, what kind of noise, how the room echoes,
how many different speakers we use, and how we split them so we can
honestly test if the driver learned to drive, not just memorized this one
track.

## 2. `seed: 42`

### 🧠 Intuition
Every "random" choice in this pipeline — which noise clip pairs with which
sentence, what SNR is picked, whether reverb triggers — is generated by a
pseudo-random number generator (PRNG). A PRNG isn't truly random; it's a
deterministic formula that *looks* random, started from a number called a
seed. Same seed → same sequence of "random" choices, every single time you
run the script.

### 📐 The math (barely any, but worth seeing)
A PRNG is a function `next_value = f(previous_state)`. The seed sets the
very first `previous_state`. Change the seed, and the entire sequence that
follows is different — but for a *fixed* seed, it's identical every run,
on any machine.

### 💻 The code
```python
import random
rng = random.Random(42)   # same seed
print(rng.random())        # always prints the same number, every run
```

### 🔗 The connection
This is why `mixing.py` and `augment.py` accept an `rng` object instead of
calling the global `random` module directly — it makes every "random"
decision traceable to one seed. Why does this matter for us specifically?
**Reproducibility.** If your model trains well (or badly) on this dataset,
you need to be able to rebuild the *exact same* dataset later to debug it,
or to prove to someone else your results aren't a fluke of a lucky random
draw. `42` itself has no special meaning — it's just a fixed, memorable
choice; any fixed integer works identically.

## 3. `sample_rate: 16000`

### 🧠 Intuition
Sound is a continuous wave — air pressure changing smoothly over time. A
computer can't store "continuous"; it has to take snapshots. Sample rate is
*how many snapshots per second* we take. 16000 (16 kHz) means we record the
sound pressure 16,000 times every second.

Analogy: think of a flipbook animation. More pages per second of footage =
smoother motion, but a bigger flipbook. Audio sampling is the same trade:
higher sample rate = more faithful reproduction of the original sound wave,
but more data to store and process.

### 📐 The math
The **Nyquist theorem** says: a sample rate of `f_s` Hz can faithfully
capture frequencies up to `f_s / 2` Hz (called the Nyquist frequency).
Above that, higher frequencies get misrepresented as lower ones — an
artifact called *aliasing*.

- `f_s = 16000` Hz → Nyquist frequency = 8000 Hz.
- Human speech's most important content (the parts that carry
  intelligibility — consonants, formants) lives mostly under 8 kHz.
- Compare: music is typically sampled at 44,100 Hz (CD quality) because
  music has meaningful energy up to ~20 kHz (the edge of human hearing).

So 16 kHz is a deliberate choice: it's the standard for **speech-only**
tasks (telephony, speech recognition, speech enhancement) because it
captures everything relevant to intelligibility while using roughly a third
of the storage/compute that 44.1 kHz would need. This isn't an arbitrary
config value — it's the sample rate the base model (dns48) was itself
trained at, so we must match it exactly, or every downstream tensor shape
and frequency-domain calculation would be wrong.

### 💻 The code
```python
import soundfile as sf
data, sr = sf.read("speech.wav")
print(sr)  # must print 16000 for this project — mismatches raise
           # RuntimeError in build_dataset.py's _load_wav(), by design
```

### 🔗 The connection
This is why `build_dataset.py`'s `_load_wav()` raises an error instead of
silently resampling when a file's sample rate doesn't match — a silent
resample would quietly change every file's duration and frequency content
in a way that's easy to miss until training behaves strangely.

## 4. The `dataset:` block — where the raw audio comes from

We need two ingredients: **clean speech** (what we want the model to
recover) and **noise** (what we want it to learn to remove). Each dataset
below supplies one or the other.

### 4a. `librispeech` — the clean speech

```yaml
librispeech:
  subset: "dev-clean"
  url: "https://www.openslr.org/resources/12/dev-clean.tar.gz"
  target_utterances_min: 2000
  target_utterances_max: 2500
```

**What it is:** LibriSpeech is a large public dataset of people reading
audiobooks aloud, released by a research group (OpenSLR) specifically for
speech research. It comes pre-split into subsets; `dev-clean` is a small,
high-quality subset (clean, low-noise recordings, used originally for
"development"/validation in speech-recognition research) — perfect for us
because we want *pristine* speech to intentionally corrupt ourselves. If we
started from already-noisy speech, we wouldn't know the true "clean"
target.

**Why `dev-clean` specifically, not `train-clean-360` (the huge one)?**
`dev-clean` is ~2,700 utterances total — big enough to have real speaker
and content diversity, small enough to download and process quickly on a
laptop. The huge training subsets (hundreds of hours) would take far
longer to download/process for no benefit at this project's scale — we're
fine-tuning a pretrained model, not training from scratch (project rule 6), so we don't need millions of examples.

**Why `target_utterances_min: 2000` / `max: 2500`?** This is a sanity
check the download script uses to confirm the download succeeded
completely (not truncated) without hardcoding the *exact* count, since
minor dataset-version differences can shift it slightly.

**Crucially: LibriSpeech's folder structure encodes the speaker ID:**
```
librispeech/LibriSpeech/dev-clean/<speaker_id>/<chapter_id>/<utterance>.flac
```
This is *why* speaker-disjoint splitting (section 6) is even possible —
the dataset organizers already tell us who's speaking, just via the file
path.

### 4b. `musan` — general-purpose noise

```yaml
musan:
  url: "https://www.openslr.org/resources/17/musan.tar.gz"
  category: "noise"
```

**What it is:** MUSAN (**MUS**ic, **S**peech, **A**nd **N**oise) is another
OpenSLR dataset, containing three categories of audio: music, speech, and
general noise (traffic, wind, crowd chatter, engines, static, etc.). We
only use the `noise` category — hence `category: "noise"` — because we
want the model to learn "remove sounds that aren't speech," not "remove
music" or "remove other people talking."

**Why do we need this at all, if the whole point is gunshots?** Real
battlefield audio isn't *just* gunshots — it's gunshots layered on top of
wind, vehicle engines, generic ambient noise. If we only ever trained the
model against gunshot noise, it would overfit to that one noise signature
and fail badly the moment there's also wind or engine hum in the recording.
MUSAN gives broad, generic noise coverage so the model learns "noise" as a
general concept, not "this one specific sound."

### 4c. `urbansound8k` — labeled gunshot sounds

```yaml
urbansound8k:
  url: "https://zenodo.org/records/1203745/files/UrbanSound8K.tar.gz"
  target_class: "gun_shot"
  expected_clip_count: 300
```

**A correction worth explaining, not hiding:** this project originally
planned to use **ESC-50** (**E**nvironmental **S**ound **C**lassification,
50 classes) here — a dataset of 2,000 short environmental sound clips
across 50 categories, each with exactly 40 clips. The plan was to extract
its `gun_shot` category. When the download script actually ran, it
extracted **0** gunshot clips — because ESC-50's real 50 categories
(checked directly against its published metadata) do not include a
gunshot/firearm class at all. The closest entries are `fireworks` and
`glass_breaking`, which are not gunshots. This was a genuine mistake in
the original dataset selection, not a bug in the download code — worth
knowing about because "the code ran without crashing" and "the code did
the right thing" are different questions, and this is a clean example of
the gap between them.

**What replaced it — UrbanSound8K:** a dataset of 8,732 short (≤4s) urban
sound clips across 10 categories — air conditioner, car horn, children
playing, dog bark, drilling, engine idling, **gun_shot**, jackhammer,
siren, street music. Unlike ESC-50, it genuinely has a gunshot class
(several hundred clips), and its Zenodo hosting offers a direct, scriptable
download link (no manual click-through), which the Kabealo dataset below
does not.

**Why this dataset, and why does the config expect ~300 clips minimum?**
UrbanSound8K's gun_shot class has roughly 370–390 clips in the published
dataset (the exact count isn't pinned down in public documentation to a
single number), so `expected_clip_count: 300` is set as a conservative
lower bound — high enough to catch a genuine extraction failure (like the
ESC-50 case above, which would have shown 0), low enough to not falsely
flag a healthy download as broken over minor version differences. These
few hundred clips alone still aren't enough diversity (same limited set of
recording conditions) — which is exactly why we also pull in a second,
much larger, independent gunshot source next.

**A practical note on this specific dataset:** its tarball bundles *all
10* categories together (~6GB total), not gun_shot alone. `download.py`
downloads the whole archive, extracts only the `gun_shot`-labeled clips
(matched via the accompanying `UrbanSound8K.csv` metadata file, which
tells you which class and which fold-subfolder each clip lives in), then
deletes the extracted archive to avoid keeping ~6GB of unrelated audio
(car horns, jackhammers, etc.) sitting on disk for no reason.

### 4d. `gunshots` (Kabealo et al. / Zenodo) — the bulk of gunshot diversity

```yaml
gunshots:
  zenodo_record_id: "7004819"
  zenodo_url: "https://zenodo.org/records/7004819"
  sample_min: 800
  sample_max: 1200
```

**What it is:** "A multi-firearm, multi-orientation audio dataset of
gunshots" (Kabealo, Wyatt et al., *Data in Brief*, 2023), hosted on Zenodo
at [record 7004819](https://zenodo.org/records/7004819). It contains 2,148
gunshot samples across 4 firearms, recorded from 27 microphones, 9 phones,
and Raspberry Pi mics placed at different positions/orientations around an
outdoor firing range. Sampling 800–1200 clips from it gives real diversity
— different firearm types, distances, mic orientations — something the few
hundred UrbanSound8K clips alone can't provide.

**Why is this still a manual download step, even with a known record ID?**
Zenodo doesn't offer a simple, stable, scriptable download link for every
record — some (including this one) are gated behind a manual click-through
on the web page (terms acceptance, etc.), so a script can't just `curl` the
archive directly. Rather than the pipeline guessing at a direct file URL
that might not exist or silently downloading the wrong thing,
`download.py` detects the data is missing and prints exact manual steps
pointing at the record above. This is a deliberate "ask, don't guess"
design per this project's rules — better to pause and tell you exactly
what to do than fail in a confusing way three steps later.

## 5. The `mixing:` block — how we build a noisy example

```yaml
mixing:
  snr_db_min: -5
  snr_db_max: 15
  noise_categories: [gunshot, stationary, general]
  eps: 1.0e-8
```

This is the heart of the whole pipeline: **given clean speech and a noise
clip, how loud do we make the noise relative to the speech?**

### 🧠 Intuition: what is SNR?
SNR = **Signal-to-Noise Ratio**. It answers: "how much louder is the thing
you want to hear (signal = speech) than the thing you don't (noise)?"

Analogy: imagine trying to hear a friend talk. If they're speaking normally
in a quiet library, their voice completely dominates — high SNR, easy to
understand. If they're whispering next to a running jackhammer, the
jackhammer dominates — low (or negative) SNR, nearly impossible to
understand. SNR is a single number that captures "how hard is it to hear
the speech over the noise."

### 📐 The math
SNR is measured in **decibels (dB)**, a logarithmic scale:

```
SNR(dB) = 20 · log10( RMS(signal) / RMS(noise) )
```

- `RMS` (Root Mean Square) is a way of measuring a waveform's average
  "loudness" or energy — square every sample (to make everything
  positive), average those squares, take the square root. It's a more
  meaningful "average loudness" than a plain average, because a plain
  average of a sound wave (which swings positive and negative) would
  average out to roughly zero even for a very loud sound.
- The ratio `RMS(signal)/RMS(noise)` compares how energetic the speech is
  versus the noise.
- `log10` and the `20×` multiplier convert that ratio into decibels —
  logarithmic because human hearing itself perceives loudness
  logarithmically (a sound has to get *much* more energetic before we
  perceive it as "twice as loud").

**What the extremes mean:**
- **SNR = 0 dB**: signal and noise have equal RMS energy — genuinely hard
  to understand speech.
- **SNR > 0 dB (positive)**: signal is louder than noise. +15 dB means
  signal is roughly 5.6× louder in RMS terms — noise is present but speech
  clearly dominates.
- **SNR < 0 dB (negative)**: noise is *louder* than the speech itself.
  -5 dB means noise has about 1.8× more RMS energy than the speech — a
  genuinely hostile listening condition, like trying to talk over gunfire
  a few meters away.

### Why `-5 dB` to `+15 dB` specifically, for *this* project?
This range is chosen to span from "genuinely hostile" to "mildly
annoying":
- The **-5 dB end** simulates realistic close-range battlefield conditions
  — a gunshot or explosion nearby can genuinely overpower speech. If we
  never trained on such harsh conditions, the model would have no idea
  what to do when it encounters them in deployment.
- The **+15 dB end** simulates milder conditions — background noise is
  present and audible but not overwhelming (e.g., distant traffic, wind).
  We still need examples like this so the model doesn't *over-correct* and
  start distorting speech that barely had any noise to begin with.
- Randomly sampling *within* this range for every single pair (rather than
  using one fixed SNR for the whole dataset) is what makes the model robust
  across the full spectrum of real-world conditions, instead of only being
  good at one specific noise loudness.

### 💻 The code — what `mix_pair()` actually does
```python
# from src/data/mixing.py, simplified
clean_rms = rms(clean)                     # how loud is the speech?
noise_rms = rms(noise)                     # how loud is the noise, raw?

target_snr_db = random.uniform(-5, 15)     # pick a difficulty for this example
target_noise_rms = clean_rms / (10 ** (target_snr_db / 20))
scale = target_noise_rms / noise_rms       # how much to turn the noise up/down
scaled_noise = noise * scale               # actually rescale it

noisy = clean + scaled_noise               # sum = our fake noisy recording
```
The key insight: we don't just add the noise as-is — we **compute exactly
how loud it needs to be** to hit our randomly chosen target SNR, then scale
it to match, *then* add it. This is what "SNR-targeted mixing" means: the
loudness of the noise is derived from the target ratio, not left to
whatever the original recording's volume happened to be.

### What is `eps: 1.0e-8` doing?
Look at the formula: `scale = target_noise_rms / noise_rms`. If a noise
clip happens to be near-total silence (RMS ≈ 0 — e.g., padding at the end
of a short clip), we'd be dividing by (almost) zero, which either crashes
the program or produces an absurd, huge scale factor that corrupts the
mix. `eps` is a tiny floor value (`0.00000001`) — the code does
`noise_rms = max(noise_rms, eps)` so the division always has a safe,
non-zero denominator. This is a classic numerical-stability guard, not a
meaningful physical quantity — the value `1e-8` is just "small enough to
never matter for real audio, but never exactly zero."

### Why `noise_categories: [gunshot, stationary, general]` — tagging, not just mixing
Every mixed pair records *which kind* of noise was used, not just that
*some* noise was used. This matters because it lets us later ask a much
sharper question than "does the model work?" — namely, "does the model
work well on gunshots specifically, versus generic wind noise?" (referred
to in this project as the **Tier-1 per-noise-type breakdown**). If we threw
away the category label at mix time, we could never recover it later — a
model might report a great *average* score while quietly failing hard on
exactly the noise type this project cares most about (gunshots). Tagging
it now, at generation time, means the manifest (`manifests/*.json`) can
carry `noise_category` all the way through to evaluation.

## 6. The `augment:` block — reverb and clipping

Mixing gives us noisy speech. Augmentation adds two *more* realistic
distortions on top, each simulating a specific physical phenomenon that a
real deployed microphone would encounter.

### 6a. Reverb — simulating physical spaces

```yaml
reverb:
  probability: 0.3
  room_scale_min: 0.1
  room_scale_max: 1.0
  reverberance_min: 20
  reverberance_max: 80
```

### 🧠 Intuition
Clap your hands in an empty gymnasium versus outdoors in an open field. In
the gym, you hear the clap, then a trailing "shhh" as the sound bounces off
walls, floor, and ceiling and arrives at your ears slightly delayed, over
and over, fading out. That trailing echo-like decay is **reverberation
(reverb)**. Every enclosed or semi-enclosed space — a room, a vehicle
cabin, a corridor, a bunker — adds some amount of this effect to any sound
recorded in it, including speech.

**Why simulate it at all?** If we only trained the model on noise mixed
into speech recorded in a perfectly "dry" (echo-free) studio environment,
the model would never learn to handle the fact that real speech, recorded
in a real room or vehicle, already carries reverb *before* the noise is
even added. Without this, the model might treat reverb tails as "noise to
remove" and over-aggressively distort speech, or fail to generalize to
real recordings at all.

### 📐 The math
Physically, reverb is what happens when a sound source's waveform is
**convolved** with a room's *impulse response* (IR) — a signature waveform
that describes exactly how that specific room reflects and decays sound
over time (loud multiple bounces close together for a small room, sparser
longer-delayed bounces for a large hall).

```
reverberant_signal = original_signal  *  room_impulse_response
                                      ↑
                               (convolution, not multiplication)
```

We don't have real measured room impulse responses on hand, so this
project **synthesizes** a plausible fake one: random noise, shaped by an
exponential decay curve, standing in for "a room's echo signature":

```python
decay = exp(-t / time_constant)     # bigger time_constant = slower fade = "bigger" room
ir = random_noise * decay
```

- **`room_scale`** (0.1 to 1.0) controls how *long* the synthetic impulse
  response is — physically, this maps to room size: a tiny room's echoes
  die out almost instantly, a large hall's echoes ring on much longer.
  0.1 to 1.0 spans "small room / vehicle cabin" up to "larger hall/bunker,"
  covering plausible deployment environments without going to absurd
  extremes (a stadium-sized reverb tail would be unrealistic for this
  project's context).
- **`reverberance`** (20 to 80) controls how *slowly* that impulse response
  decays — i.e., how "wet"/present the echo feels, independent of room
  size. Low reverberance = the echo fades out fast even within the room's
  time window (more absorptive surfaces — carpet, fabric, bodies). High
  reverberance = a more "ringing," reflective space (bare concrete, metal
  vehicle interior).
- **`probability: 0.3`** — we don't want *every* training example to have
  reverb; real speech is sometimes recorded close to the mic with almost no
  room effect at all (e.g., a headset mic). Applying reverb to only 30% of
  examples keeps a healthy mix of "dry" and "reverberant" speech, so the
  model doesn't overfit to assuming reverb is always present.

### 💻 The code
```python
# from src/data/augment.py, simplified
ir = synthesize_impulse_response(room_scale, reverberance)
reverberant = conv1d(waveform, ir)   # the actual "echo" operation
```

### 6b. Clipping — simulating a microphone/amplifier hitting its limit

```yaml
clipping:
  probability: 0.15
  clip_percentile_min: 0.95
  clip_percentile_max: 0.999
```

### 🧠 Intuition
Every microphone and amplifier has a maximum signal level it can represent.
If the actual sound is louder than that (a very loud gunshot right next to
the mic, or a signal that's been amplified too much), the top and bottom of
the waveform get "chopped flat" instead of following the sound's real
shape — this is **clipping**. You've heard it as the harsh, crackly
distortion when someone shouts too close to a cheap mic, or a phone
speaker maxed out at full volume.

**Why simulate it?** Gunshots are exactly the kind of extremely loud,
sudden transient that *causes* real microphones to clip in the field. If
our training data never includes clipped audio, the model has never seen
this specific, very common distortion and may handle it poorly at
inference — producing strange artifacts on exactly the loud gunshot
moments we most care about getting right.

### 📐 The math
Clipping is a hard limit — anything above a threshold gets flattened to
that threshold:

```
clipped(x) = clamp(x, -threshold, +threshold)
```

Where does `threshold` come from? Rather than a fixed absolute number (which
wouldn't generalize across clips of different volumes), this code picks the
threshold as a **percentile of that specific waveform's own amplitude
distribution**:

```python
threshold = quantile(abs(waveform), percentile)   # percentile in [0.95, 0.999]
```

- At `percentile = 0.999`: only the loudest 0.1% of samples get clipped —
  very mild, subtle clipping.
- At `percentile = 0.95`: the loudest 5% of samples get flattened — much
  harsher, more audible distortion.
- Sampling `percentile` randomly between these two bounds per example gives
  a *range* of clipping severity, from barely-there to clearly audible,
  again so the model learns to handle mild and harsh cases alike.
- **`probability: 0.15`** — lower than reverb's 0.3, because clipping is a
  more severe, less universally-present distortion (not every recording
  device or every gunshot causes clipping) — we want it present often
  enough to matter, but not so often that "everything is clipped" becomes
  the model's assumption.

### 💻 The code
```python
threshold = torch.quantile(waveform.abs().flatten(), percentile)
clipped = torch.clamp(waveform, min=-threshold, max=threshold)
```

### 🔗 The connection (both augmentations together)
Mixing (section 5) teaches the model "there's an unwanted sound layered on
top of speech, at varying loudness." Reverb and clipping each teach a
*different, independent* real-world corruption on top of that: reverb
teaches "the recording space itself changes how the sound arrives,"
clipping teaches "sometimes the recording equipment itself can't represent
how loud the real event was." A denoiser that's only ever seen mixing
without these two would work in a lab-clean setting but degrade
noticeably on real battlefield recordings, which almost always carry both
effects to some degree.

## 7. The `split:` block — train / val / test, by speaker

```yaml
split:
  train_ratio: 0.8
  val_ratio: 0.1
  test_ratio: 0.1
```

### 🧠 Intuition
You always need three separate pools of data when building a model:
- **train**: what the model actually learns from.
- **val** (validation): used *during* development to check progress and
  tune choices, without touching the final exam.
- **test**: touched exactly once, at the very end, to report an honest,
  unbiased score — the "final exam" the model has never seen in any form.

The critical detail here is **"by speaker."** LibriSpeech utterances are
grouped by who's speaking (section 4a). If we split by *utterance*
(individual sentences) instead of by *speaker*, the same person's voice
could appear in both train and test. The model could then partially
"cheat" — learning to recognize and denoise *that specific person's voice
characteristics* rather than learning to denoise speech in general. Its
test score would look artificially good, but it would perform worse on any
new voice it's never heard, which defeats the entire purpose of a held-out
test set. This is called **speaker/identity leakage**, and splitting by
speaker (assigning each speaker's *entire* set of utterances to exactly one
split) is the standard fix.

### 📐 The math
Nothing complicated: for `N` total speakers, shuffle them (using the seed
from section 2, so it's reproducible), then take the first `0.8 × N` as
train speakers, the next `0.1 × N` as val speakers, and the rest as test
speakers. Every utterance from a given speaker follows that speaker into
whichever split they landed in.

### 💻 The code
```python
# from src/data/build_dataset.py, simplified
speaker_ids = list(by_speaker.keys())
rng.shuffle(speaker_ids)                       # reproducible random order
n_train = int(len(speaker_ids) * 0.8)
n_val   = int(len(speaker_ids) * 0.1)
train_speakers = speaker_ids[:n_train]
val_speakers   = speaker_ids[n_train:n_train+n_val]
test_speakers  = speaker_ids[n_train+n_val:]
```

### Why 80/10/10 specifically?
This is a very standard default split ratio in ML generally, not something
unique to audio: give the model the large majority of data to learn from
(80%), keep a moderate slice for tuning decisions during development
(10%), and reserve an equally-sized slice purely for final, honest
reporting (10%). With a dataset in the low thousands of utterances (from
`dev-clean`'s ~2000–2500), 10% still gives a few hundred utterances per
val/test split — enough to get a statistically meaningful score without
starving the training set.

## 8. The `output:` block

```yaml
output:
  bit_depth: "PCM_16"
  format: "wav"
```

### 🧠 Intuition
This controls how the final noisy/clean audio pairs are actually saved to
disk, as opposed to how they're processed in memory.

- **`format: "wav"`** — WAV is an *uncompressed* audio container. Unlike
  MP3, which throws away some audio detail to save space (lossy
  compression), WAV stores the actual waveform samples directly. For a
  research/training dataset, we never want compression artifacts sneaking
  into our "ground truth" clean audio — that would mean the model is
  partially learning to reproduce MP3 compression artifacts as if they were
  real speech content.
- **`bit_depth: "PCM_16"`** — **bit depth** is a second, separate axis from
  sample *rate* (section 3): sample rate is *how often* we measure the
  wave, bit depth is *how precisely* we record each individual measurement.
  16-bit PCM (Pulse Code Modulation) means each sample is stored as one of
  65,536 (`2^16`) possible amplitude levels. This is the standard bit depth
  for speech and telephony work (and matches what LibriSpeech and most
  speech datasets already ship as) — enough precision that quantization
  noise (rounding error from only having 65,536 discrete levels instead of
  a truly continuous value) is far below the level of audible noise we're
  intentionally adding anyway.

### 🔗 The connection
Together, `sample_rate: 16000` + `bit_depth: PCM_16` fully define the
"resolution" of every audio file this pipeline produces — one axis for time
(how often), one axis for amplitude (how precisely). Both are chosen to
match what's standard and sufficient for speech, and critically, to match
what the pretrained dns48 model expects as input — mismatching either one
would silently break the model's assumptions about its input data.

## Summary table

|---|---|---|
| `seed` | Reproducibility of all random choices | Fixed integer so the dataset can be rebuilt identically |
